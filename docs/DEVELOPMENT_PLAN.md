# LiteShop 开发计划

## 当前开发进展（0.3.0）

| 阶段 | 已实现 | 尚待完成 |
| --- | --- | --- |
| Phase 0-1 | 工程、许可、SQLite 迁移与账本基础、CI | 预约/资源等扩展表与业务 |
| Phase 2-3 | 会员编辑/停用、储值卡/次卡、充值消费退款、积分、幂等与账本审计 | 卡类型配置 UI、完整冲正/积分过期等 |
| Phase 4 | 中文本地 Web 工作台、本地 API、连接状态、待确认请求重试 | API 19 实机操作与长期稳定性验收 |
| Phase 5 | 事务内 outbox、后台上传、逐事件确认、幂等/顺序校验及固定周期重试 | 指数退避、错误诊断、游标下载与冲突处理 |
| Phase 6 | API 19 独立客户端、内置 ES5 页面、本机 SQLite、事务账本与本地 Bridge | Kiosk、自启、备份恢复、USB 打印、真机验收 |
| Phase 7-9 | Docker Cloud API、原始事件/只读投影、内部查询和微信 API 契约、Docker CI | 设备/微信身份认证、备份、预约、小程序与行业插件 |

产品架构固定为「安卓机顶盒独立客户端 → 云端服务 → 微信小程序」。机顶盒是门店唯一主机，HDMI 接显示器，USB 接键鼠、打印机和扫码枪；数据与文件保存在机顶盒，离线完成营业。电脑只用于开发和测试。

## 1. 产品路线

LiteShop 采用 **机顶盒本地优先 → 云端同步 → 微信小程序** 的路线：

```text
Phase 1-5：单机离线内核
        ↓
Phase 6：Android 独立客户端
        ↓
Phase 7：云端同步与备份
        ↓
Phase 8：微信会员端与通知
        ↓
Phase 9：行业插件与商业化能力
```

每个阶段都应产生可运行、可验证的结果，不等待完整云端系统完成后才可使用。

## 2. 里程碑

### Phase 0：工程初始化

目标：建立仓库约定和可评审文档。

- 初始化目录、README、开发计划和决策记录
- 确定兼容目标：Android 4.4/API 19、1 GB RAM、键鼠输入
- 确定金额、ID、账本和同步事件规则
- 建立基础 CI/格式化/测试入口
- 固定个人免费、商用授权制度和微信小程序 API 预留契约

验收：新开发者可以仅通过 README 理解产品边界、架构和下一步工作。

### Phase 1：SQLite 数据层

目标：把业务地基做成可迁移、可测试的本地数据库。

- 建立 `shop`、`device`、`member`、`member_tag`、`card_type`、`member_card`
- 建立 `transaction`、`transaction_item`、`points_account`、`points_transaction`
- 建立 `staff`、`appointment`、`service`、`resource`
- 建立 `operation_log`、`sync_event`、`sync_state`
- 添加外键、索引、软删除字段和 migration 版本
- 编写 repository 接口，隔离数据访问；Android 当前由 LocalStore 封装 SQL，后续可按规模拆分

验收：空库可从零迁移；升级迁移可重复执行；关键约束有自动化测试。

### Phase 2：会员与卡业务

目标：完成门店每天最常用的会员操作。

- 会员新增、修改、停用、手机号/会员号搜索
- 卡类型配置、开卡、挂失、停用、有效期
- 储值卡余额和次卡剩余次数
- 会员详情页展示余额、积分、最近流水

验收：离线状态下完成完整会员工作流，数据重启后仍可读取。

### Phase 3：交易账本与积分

目标：保证钱和次数可以追溯、校验和重算。

- 充值、消费、退款、赠送、人工调整、冲正
- 每笔交易记录余额前值、变动值、余额后值、操作人和设备
- 交易失败时整笔 SQLite transaction 回滚
- 积分赚取、扣除、兑换、过期流水
- 提供余额重算和账本一致性检查命令

验收：模拟断电/重复提交后账本不多记、不少记；余额可由流水重建。

### Phase 4：本地 UI

目标：做出适合电视大屏和键鼠的可用界面。

- 使用 HTML5/CSS3/ES5，控制首版脚本体积
- 首页、会员搜索、会员详情、充值/消费/扣次弹窗
- 大按钮、高对比度、明确的成功/失败提示
- 键盘焦点顺序和扫码枪（键盘模拟输入）
- 显示离线状态、待同步数量和最近操作

验收：在现代浏览器和 Android 4.4 WebView 兼容性环境中完成核心流程。

### Phase 5：同步事件引擎

目标：网络恢复后可靠同步，不影响本地营业。

- 业务提交时生成 `sync_event`
- `PENDING → UPLOADING → SYNCED/FAILED` 状态机
- `event_id` 幂等重试、退避和错误记录
- 下载游标和事件顺序
- 资料类实体的最后写入规则；财务类实体只追加事件
- 导出待同步事件，便于诊断和人工恢复

验收：重复上传同一事件只产生一次业务结果；中断后可继续同步。

### Phase 6：Android Terminal

目标：让旧安卓盒子像专用商用终端一样启动和运行。

- 独立 Android APK + 本机 SQLite + WebView，后续增加 Kiosk 模式
- 加载内置本地 Web UI，不依赖网络启动
- JavaScript Bridge：设备信息、备份、打印任务和扫码输入
- 开机自启动、横屏、大屏适配、异常恢复
- 针对 Android 4.4 的 API 和 WebView 特性测试

验收：断网、重启、低内存场景下仍能完成 Phase 2-4 的核心流程。

### Phase 7：门店版与云端 API

目标：支持多个独立机顶盒账本上传至云端，连接微信小程序；每个门店首版只设一台营业主机。Terminal A/B 拥有独立 ID 与本地账本，当前不提供同店共享余额或跨店通兑。

- 门店、设备、员工账号和角色
- HTTPS API、设备授权和同步端点
- 服务端事件幂等表和处理结果
- 按 `docs/API_WECHAT_MINIPROGRAM.md` 实现微信小程序只读会员查询和预约接口
- 云端备份、恢复和换机绑定
- 监控、审计和数据导出

验收：机顶盒断网期间事件可恢复上传；服务端重复请求无副作用；小程序展示同步时间，不能覆盖本地账本。

### Phase 8：微信会员端

目标：让会员在云端可选服务中查询和预约。

- 会员绑定、余额/积分/卡包只读查询（接口预留见 `docs/API_WECHAT_MINIPROGRAM.md`）
- 消费记录和预约
- 微信通知配额（首版可提供每月 1 次体验通知）
- 终端扫码绑定店铺和云服务

验收：微信端不直接修改余额；预约和查询状态可追溯到云端事件。

### Phase 9：行业插件

目标：在不修改通用内核的情况下支持行业差异。

- Beauty：服务、技师、排班、疗程和分佣
- Carwash：车辆、工位、服务套餐和工单
- Gym：课程、教练和课次
- Tutoring：课程、教师、教室和课表

验收：行业插件只依赖 Core 的公开接口，卸载插件不破坏通用会员数据。

## 3. 质量门槛

- 所有金额、余额和积分测试使用整数，不使用浮点数。
- 核心用例必须覆盖成功、回滚、重复提交和重启恢复。
- 迁移脚本在空库、旧版本库和重复执行场景通过测试。
- 同步测试必须验证幂等、重试、乱序和冲突处理。
- 终端发布前在 Android 4.4 和至少一个较新 Android 版本上验证。
- 每个阶段更新 README、数据字典和变更日志。

## 4. 暂不做

- 不在 MVP 阶段绑定单一行业。
- 不把云端作为本地营业的前置依赖。
- 不直接复制 AGPL 项目作为商业底座。
- 不在首版引入复杂前端框架、大型 UI 库或重型 Android 依赖。
- 不允许微信端绕过门店交易账本直接改余额。

## 5. 下一步执行顺序

1. 完成 API 19 和较新 Android 的构建、原生数据库测试及真机验收，重点检查离线交易、幂等重试、重启与低内存恢复。
2. 实现本机 SQLite 一致性备份、导出与恢复；支持换机前校验，不直接复制正在写入的数据库。
3. 按实际 USB 打印机型号实现授权、驱动与持久打印队列；完成键鼠及 HID 扫码枪专项验收。
4. 增加设备启动恢复、Kiosk、门店配置及员工登录权限。
5. 在已完成的上传/幂等投影骨架上完善设备注册、分店鉴权、退避诊断、云端备份和下载游标，再推进微信登录、会员绑定和预约。
6. 验证多个独立终端连接同一 Cloud API，完善每店每设备授权；共享会员及跨店消费单独设计。当前不引入门店电脑。
