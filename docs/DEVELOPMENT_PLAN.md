# LiteShop 开发计划

## 当前开发进展（0.2.0）

| 阶段 | 已实现 | 尚待完成 |
| --- | --- | --- |
| Phase 0-1 | 工程、许可、SQLite 迁移与账本基础、CI | 预约/资源等扩展表与业务 |
| Phase 2-3 | 会员编辑/停用、储值卡/次卡、充值消费退款、积分、幂等与账本审计 | 卡类型配置 UI、完整冲正/积分过期等 |
| Phase 4 | 中文本地 Web 工作台、本地 API、连接状态、待确认请求重试 | API 19 实机操作与长期稳定性验收 |
| Phase 5 | 事务内 outbox、待同步数量显示 | 同步状态机、上传下载与冲突处理 |
| Phase 6 | API 19 外壳、内置 ES5 页面、局域网 Bridge、连接设置与重载 | 原生单机内核、Kiosk、自启、备份打印、真机验收 |
| Phase 7-9 | 微信小程序 API 契约预留 | 云端、小程序、行业插件 |

按当前需求优先推进 Phase 4 和 Phase 6 接入工程，不将尚未实现的条目标记为完成。本版 Android 的业务数据保存在门店电脑 SQLite 中，局域网服务是交易前置条件。

## 1. 产品路线

LiteShop 采用 **Local-first → Store → Cloud** 的路线：

```text
Phase 1-5：单机离线内核
        ↓
Phase 6：Android 终端壳
        ↓
Phase 7：门店局域网与云同步
        ↓
Phase 8：微信会员端与通知
        ↓
Phase 9：行业插件与商业化能力
```

每个阶段都应产生可运行、可验证的结果，不等待完整云端系统完成后才可使用。

## 2. 里程碑

### Phase 0：工程初始化

目标：建立仓库约定和可评审文档。

- 初始化目录、README、开发计划和决策记录
- 确定兼容目标：Android 4.4/API 19、1 GB RAM、键鼠输入
- 确定金额、ID、账本和同步事件规则
- 建立基础 CI/格式化/测试入口
- 固定个人免费、商用授权制度和微信小程序 API 预留契约

验收：新开发者可以仅通过 README 理解产品边界、架构和下一步工作。

### Phase 1：SQLite 数据层

目标：把业务地基做成可迁移、可测试的本地数据库。

- 建立 `shop`、`device`、`member`、`member_tag`、`card_type`、`member_card`
- 建立 `transaction`、`transaction_item`、`points_account`、`points_transaction`
- 建立 `staff`、`appointment`、`service`、`resource`
- 建立 `operation_log`、`sync_event`、`sync_state`
- 添加外键、索引、软删除字段和 migration 版本
- 编写 repository 接口，业务层不得直接拼接 SQL

验收：空库可从零迁移；升级迁移可重复执行；关键约束有自动化测试。

### Phase 2：会员与卡业务

目标：完成门店每天最常用的会员操作。

- 会员新增、修改、停用、手机号/会员号搜索
- 卡类型配置、开卡、挂失、停用、有效期
- 储值卡余额和次卡剩余次数
- 会员详情页展示余额、积分、最近流水

验收：离线状态下完成完整会员工作流，数据重启后仍可读取。

### Phase 3：交易账本与积分

目标：保证钱和次数可以追溯、校验和重算。

- 充值、消费、退款、赠送、人工调整、冲正
- 每笔交易记录余额前值、变动值、余额后值、操作人和设备
- 交易失败时整笔 SQLite transaction 回滚
- 积分赚取、扣除、兑换、过期流水
- 提供余额重算和账本一致性检查命令

验收：模拟断电/重复提交后账本不多记、不少记；余额可由流水重建。

### Phase 4：本地 UI

目标：做出适合电视大屏和键鼠的可用界面。

- 使用 HTML5/CSS3/ES5，控制首版脚本体积
- 首页、会员搜索、会员详情、充值/消费/扣次弹窗
- 大按钮、高对比度、明确的成功/失败提示
- 键盘焦点顺序和扫码枪（键盘模拟输入）
- 显示离线状态、待同步数量和最近操作

验收：在现代浏览器和 Android 4.4 WebView 兼容性环境中完成核心流程。

### Phase 5：同步事件引擎

目标：网络恢复后可靠同步，不影响本地营业。

- 业务提交时生成 `sync_event`
- `PENDING → UPLOADING → SYNCED/FAILED` 状态机
- `event_id` 幂等重试、退避和错误记录
- 下载游标和事件顺序
- 资料类实体的最后写入规则；财务类实体只追加事件
- 导出待同步事件，便于诊断和人工恢复

验收：重复上传同一事件只产生一次业务结果；中断后可继续同步。

### Phase 6：Android Terminal

目标：让旧安卓盒子像专用商用终端一样启动和运行。

- 最小 Android APK + WebView/Kiosk 模式
- 加载内置本地 Web UI，不依赖网络启动
- JavaScript Bridge：设备信息、备份、打印任务和扫码输入
- 开机自启动、横屏、大屏适配、异常恢复
- 针对 Android 4.4 的 API 和 WebView 特性测试

验收：断网、重启、低内存场景下仍能完成 Phase 2-4 的核心流程。

### Phase 7：门店版与云端 API

目标：支持多设备、云备份和可选远程服务。

- 门店、设备、员工账号和角色
- HTTPS API、设备授权和同步端点
- 服务端事件幂等表和处理结果
- 按 `docs/API_WECHAT_MINIPROGRAM.md` 实现微信小程序只读会员查询和预约接口
- 云端备份、恢复和换机绑定
- 监控、审计和数据导出

验收：两台终端产生的非冲突事件均可同步；服务端重复请求无副作用。

### Phase 8：微信会员端

目标：让会员在云端可选服务中查询和预约。

- 会员绑定、余额/积分/卡包只读查询（接口预留见 `docs/API_WECHAT_MINIPROGRAM.md`）
- 消费记录和预约
- 微信通知配额（首版可提供每月 1 次体验通知）
- 终端扫码绑定店铺和云服务

验收：微信端不直接修改余额；预约和查询状态可追溯到云端事件。

### Phase 9：行业插件

目标：在不修改通用内核的情况下支持行业差异。

- Beauty：服务、技师、排班、疗程和分佣
- Carwash：车辆、工位、服务套餐和工单
- Gym：课程、教练和课次
- Tutoring：课程、教师、教室和课表

验收：行业插件只依赖 Core 的公开接口，卸载插件不破坏通用会员数据。

## 3. 质量门槛

- 所有金额、余额和积分测试使用整数，不使用浮点数。
- 核心用例必须覆盖成功、回滚、重复提交和重启恢复。
- 迁移脚本在空库、旧版本库和重复执行场景通过测试。
- 同步测试必须验证幂等、重试、乱序和冲突处理。
- 终端发布前在 Android 4.4 和至少一个较新 Android 版本上验证。
- 每个阶段更新 README、数据字典和变更日志。

## 4. 暂不做

- 不在 MVP 阶段绑定单一行业。
- 不把云端作为本地营业的前置依赖。
- 不直接复制 AGPL 项目作为商业底座。
- 不在首版引入复杂前端框架、大型 UI 库或重型 Android 依赖。
- 不允许微信端绕过门店交易账本直接改余额。

## 5. 下一步执行顺序

1. 在有 JDK 17 / Gradle 8.9 / Android SDK 的环境构建 APK，执行 API 19 和较新 Android 真机验收。
2. 重点验证响应丢失后的幂等重试、重启/低内存及局域网断连恢复。
3. 实现本地 SQLite 在线备份与恢复，再接打印适配。
4. 若需 Android 单机完全脱离门店电脑运行，移植 Repository/UseCase 到原生 SQLite，沿用相同账本约束与测试用例。
5. 实现同步引擎，再按微信小程序 API 契约推进云端只读查询与预约。
